<h3 id="cn-v0.1.4">插件 0.1.4 — 已验证 DeepSeek Harness 0.1.7-rc.1（最新候选版本）</h3>

### 版本对应

| 插件版本 | 已验证的 DeepSeek Harness | npm 发布状态 |
| --- | --- | --- |
| **`0.1.4`** | **`0.1.7-rc.1`（最新 RC）**、`0.1.7-alpha.2` | 本次发布（`latest`） |
| `0.1.3` | `0.1.7-alpha.2` | 已发布 |
| `0.1.2` | `0.1.6-alpha.2` | 已发布 |

### 为什么发这个版本

官方发布了 `0.1.7-rc.1`，这是 `0.1.7` 系列的首个候选版本。本版的作用是**确认并声明对新 RC 的支持**——`0.1.7` 线的破坏性变更（侧栏行 DOM、link 插件依赖解析）`0.1.3` 已经吸收完毕，所以这次没有新的适配工作，只有兼容性确认与声明更新。三处结论都来自运行实例与官方产物本身，不是推测：

1. **在运行中的 `0.1.7-rc.1` 实例上实测通过，且用的是已发布的 `0.1.3`（COPY 安装）。** boot 图里含 `@idoall/dsh-session-colors` 且**未被新的兼容性预检禁用**；控制台输出 `build=host-routes+animated-rows marks route status=ready`；3 个真实标记的色块与行精确对齐（`left=14`＝行 `left=12`+2，`top`＝行顶+8，偏差 0）；选择器正常开关（`role=dialog`、7 个主题色、面板留在屏内）。也就是说宿主半加载、客户端 bundle、行内色块、头部选择器四条链路在 RC 上全部正常。
2. **核对了 rc.1 的实际产物。** 在 `alpha.2 → rc.1` 之间，本插件依赖的客户端/宿主契约（client-modules 加载器、`ui-workspace` 的 `Rows.tsx`/`AnimatedRows.tsx`、`ui-layout` 的 overlay、`ui-slots`、`locale`、host `webserver`、`connection`、app-boot 的 profile 解析）**没有任何源码改动**，只有版本号；唯一实质新增是 boot 的兼容性预检。
3. **预检对我们的声明判定为通过。** `evaluatePluginCompatibility` 只检查 `@deepseek-ai/dsh*` 的 peer，用 `semver.satisfies(runtime, range, { includePrerelease: true })`；我们的 `>=0.1.7-alpha.2 <0.2.0` 对 `0.1.7-rc.1` 实测为 `true`。**范围不满足时，DSH 会直接禁用该插件行**——这也是 `0.1.3` 把下界写成 `0.1.7-alpha.2` 而不是旧的 `>=0.1.6-0` 的现实理由。

### 改了什么

- **声明记录新 RC。** `dsh.compatibility.dshReleases` 现同时记录 `0.1.7-rc.1` 与 `0.1.7-alpha.2`。
- **peer 与 `dsh.engines.dsh` 范围刻意保持不变。** 仍是 `>=0.1.7-alpha.2 <0.2.0`：按 node-semver 的预发布规则，只要范围里有比较符写了同一个 `major.minor.patch`，该版本的预发布就会被接纳，所以这个范围**同时覆盖** alpha.2 与 rc.1。无需为 RC 放宽范围，也就不会顺带接纳未经测试的版本。
- **代码零改动。** 两个半边与 `0.1.3` 完全一致；本版只改声明与文档。
- **文档强调。** 中英文 README 在顶部与兼容性章节明确标注已支持最新 RC；设计记录补记了 rc.1 的预检行为与本次实测结论。

### 谁受影响

- **正在使用 `0.1.7-rc.1` 的人**：直接升级即可，本版就是为这个版本发布的。
- **从 `0.1.3` 升级的人**：**标记数据无需迁移、配置无需改动**——代码与 `0.1.3` 相同，`session-colors.json` 照旧读取。
- **仍在更旧 DSH（含 `0.1.6-alpha.2`）的人：请继续用插件 `0.1.2`。** `0.1.4` 声明的宿主要求是 `>=0.1.7-alpha.2 <0.2.0`，低于它的版本未经本轮验证。

### 兼容性与升级

```sh
dsh plugin --profile web add @idoall/dsh-session-colors@0.1.4
```

然后在 profile 的 `cordis.patch.yml` 里给一个数据目录（若尚未配置），再**重启 `dsh web`**：

```yaml
- id: dsh-session-colors
  config:
    dataDir: /absolute/path/to/profiles/web/data/dsh-session-colors
```

宿主半边只在 DSH 启动时加载，所以升级后需要重启 `dsh web`；客户端半边刷新页面即生效。不配 `dataDir` 也能用，但标记只活在宿主进程的生命周期里。

从 `0.1.3` 升级不需要任何数据操作。

### 限制

- **色块依赖 DSH 的行 DOM**：靠 ARIA role 找行、靠行自身的 `data-row-key` 取会话 id（回退到 React fiber）。DSH 大改侧栏结构后色块可能不再显示；但**不会影响点击**，因为浮层从不接收指针事件。
- **标记属于单个 DSH 实例**：两个独立的 DSH 服务之间不共享。
- **没有权限模型**：能访问该 profile 已鉴权路由的人都能读写标记。
- **只有颜色**：没有文字标签、图标或 emoji。

<h3 id="en-v0.1.4">Plugin 0.1.4 — verified against DeepSeek Harness 0.1.7-rc.1 (the latest release candidate)</h3>

### Version matrix

| Plugin version | Verified DeepSeek Harness | npm status |
| --- | --- | --- |
| **`0.1.4`** | **`0.1.7-rc.1` (latest RC)**, `0.1.7-alpha.2` | this release (`latest`) |
| `0.1.3` | `0.1.7-alpha.2` | published |
| `0.1.2` | `0.1.6-alpha.2` | published |
| `0.1.1` | `0.1.6-alpha.2` | published (documentation only) |
| `0.1.0` | `0.1.6-alpha.2` | published |

### Why this release exists

The harness published `0.1.7-rc.1`, the first release candidate on the `0.1.7`
line. This release **confirms and declares support for that RC** — `0.1.3`
already absorbed the `0.1.7` breaking changes (the sidebar row markup and the
linked-plugin dependency resolution), so there is no new adaptation work here,
only a compatibility confirmation and a declaration update. All three findings
come from the running instance and the shipped artifacts, not from inference:

1. **Verified on a running `0.1.7-rc.1` instance, using the published `0.1.3`
   (a copied install).** The boot graph contains `@idoall/dsh-session-colors` and
   the new compatibility preflight did **not** disable it; the console reports
   `build=host-routes+animated-rows marks route status=ready`; the three real
   marks' chips align exactly with their rows (`left=14` = row `left=12` + 2,
   `top` = row top + 8, zero deviation); the picker opens and closes normally
   (`role=dialog`, seven theme swatches, panel inside the viewport). Host-half
   load, client bundle, sidebar chip and header picker are all intact on the RC.
2. **Checked against the shipped rc.1 artifacts.** Between `alpha.2` and `rc.1`
   the client/host contracts this plugin depends on (the client-modules loader,
   `ui-workspace`'s `Rows.tsx`/`AnimatedRows.tsx`, `ui-layout`'s overlay,
   `ui-slots`, `locale`, the host `webserver`, `connection`, and app-boot's
   profile resolution) have **no source changes at all**, only version bumps; the
   one substantive addition is boot's compatibility preflight.
3. **The preflight accepts our declaration.** `evaluatePluginCompatibility` only
   inspects `@deepseek-ai/dsh*` peers and calls
   `semver.satisfies(runtime, range, { includePrerelease: true })`; our
   `>=0.1.7-alpha.2 <0.2.0` measures `true` for `0.1.7-rc.1`. **When the range is
   not satisfied, DSH disables the plugin row outright** — which is the concrete
   reason `0.1.3` moved the lower bound to `0.1.7-alpha.2` instead of the old
   `>=0.1.6-0`.

### What changed

- **The declaration records the new RC.** `dsh.compatibility.dshReleases` now
  records `0.1.7-rc.1` alongside `0.1.7-alpha.2`.
- **The peer and `dsh.engines.dsh` ranges deliberately stay unchanged.** They are
  still `>=0.1.7-alpha.2 <0.2.0`: under node-semver's prerelease rule a version's
  prerelease is admitted when some comparator names the same
  `major.minor.patch`, so that one range covers **both** alpha.2 and rc.1. There
  is no need to widen it for the RC, and widening would admit versions nobody
  tested.
- **Zero code change.** Both halves are identical to `0.1.3`; this release
  changes declarations and documentation only.
- **Documentation.** Both READMEs state support for the latest RC at the top and
  in their compatibility sections, and the design record now notes the rc.1
  preflight behaviour and this verification.

### Who is affected

- **Anyone on `0.1.7-rc.1`**: upgrade directly — this release exists for that
  version.
- **Upgrading from `0.1.3`**: **marks need no migration and config no change** —
  the code is identical to `0.1.3`, and `session-colors.json` is read as before.
- **Anyone still on an older DSH, including `0.1.6-alpha.2`: stay on plugin
  `0.1.2`.** `0.1.4` declares its Host requirement as
  `>=0.1.7-alpha.2 <0.2.0` and is not verified below it.

### Compatibility and upgrade

```sh
dsh plugin --profile web add @idoall/dsh-session-colors@0.1.4
```

Then give it a data directory in the profile's `cordis.patch.yml` (if it does not
have one yet) and **restart `dsh web`**:

```yaml
- id: dsh-session-colors
  config:
    dataDir: /absolute/path/to/profiles/web/data/dsh-session-colors
```

The Host half loads only at DSH boot, so an upgrade needs a `dsh web` restart; the
browser half reloads on a page refresh. It works without `dataDir`, but then marks
live only for the life of the Host process.

Upgrading from `0.1.3` needs no data operation.

### Limitations

- **Chips depend on DSH's row DOM**: rows are found by ARIA role and the Session
  id comes from the row's `data-row-key` (falling back to React internals). A
  large change to the sidebar structure can stop chips from appearing; it
  **cannot break clicking**, because the layer never accepts pointer events.
- **Marks are per DSH instance**: two independent DSH servers do not share them.
- **No permission model**: anyone who can reach the Host's authenticated routes
  for this profile can read and write marks.
- **Colour only**: no labels, icons, or emoji.
