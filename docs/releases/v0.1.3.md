### 版本对应

| 插件版本 | 已验证的 DeepSeek Harness | npm 发布状态 |
| --- | --- | --- |
| **`0.1.3`** | `0.1.7-alpha.2` | 本次发布（`latest`） |
| `0.1.2` | `0.1.6-alpha.2` | 已发布 |
| `0.1.1` | `0.1.6-alpha.2` | 已发布（仅文档） |
| `0.1.0` | `0.1.6-alpha.2` | 已发布 |

### 为什么必须适配

DSH `0.1.7-alpha.2` 改了三处插件直接依赖的东西。第 ① 处会让旧版插件**完全装不上**（`link:` 装入后宿主半边 import 失败）；第 ② 处是声明错误（范围按 node-semver 默认规则不覆盖正在运行的版本，pnpm 会报 unmet peer）；第 ③ 处是可见的行为回退（折叠/展开/重排时色块会停在滑动开始的位置）。三处都从运行实例的源码/清单里核实过，不是猜测：

1. **link 插件的依赖解析规则变了。** 0.1.7 起，只有 link 插件的 **peer** 依赖会从运行实例解析；普通 `dependencies` 只在插件自己的 `node_modules` 下查找。旧版的 `@deepseek-ai/schemastery` 是普通依赖，而本仓库并不带 `node_modules`，于是 `link:` 装入后宿主半边 import 失败，**整个插件加载不起来**。
2. **peer 范围没有覆盖这个版本。** 旧版写的是 `>=0.1.6-0 <0.2.0`。按 node-semver 的默认规则，带预发布的版本只有在某个比较符写了**同一个 `major.minor.patch`** 时才被纳入，所以 `0.1.7-alpha.2` **不满足**这个范围，pnpm 会把它报成 unmet peer。（插件市场的发现流程传了 `includePrerelease`，所以它显示的是"未知"而不是"不兼容"——声明仍然不该这么写。）
3. **侧栏行改成了动画行。** 0.1.7 给每个会话行加了 `data-row-key="session:<id>"`，并用 Web Animations API（`element.animate`）滑动行：它既不发 `transitionrun`/`transitionend`，也不改 DOM。浮层原来只在"有过渡事件"时进入有限帧的跟随循环，于是折叠/展开/重排时色块会停在滑动开始的位置。

### 改了什么

- **宿主依赖改声明为 peer。** `@deepseek-ai/schemastery` 从 `dependencies` 移到 `peerDependencies`（并保留 `devDependencies` 供本仓库自测）。这样 0.1.7 会把 link 插件的这个依赖解析到运行实例自带的 `3.18.4`，`link:` 装入不再需要本仓库先 `pnpm install`。
- **peer 范围与声明版本对齐。** `dsh-client-ui-layout` / `dsh-client-ui-conversation` 的范围改为 `>=0.1.7-alpha.2 <0.2.0`，并新增 `dsh.engines.dsh`；`dsh.compatibility.dshReleases` 记为 `0.1.7-alpha.2`。
- **会话 id 改从行自身读取。** `sessionIdOf()` 先读 `data-row-key`（`session:` 前缀），读不到再回退到 React fiber——旧构建与搜索结果行仍然走回退路径，两条路径都有边界与 `try/catch`。
- **色块跟随动画行。** 行增删、`body` class、`aria-expanded`/`hidden` 三类观察以及窗口 resize，统一走 `kick()`：立即重算一次，再进入与 CSS 过渡相同的 40 帧有限跟随循环。Web Animations 的滑动因此逐帧被跟随；与行列表无关的 body 变更只重算一次、不开跟随窗口，所以流式输出不会让测量循环常驻。
- **构建标记**改为 `host-routes+animated-rows`，便于从 DOM dump 区分"缓存客户端"。
- **文档一致性测试补强。** 原来用 `range.includes('0.1.7')` 这种字符串判断，正是它让"范围其实不覆盖运行版本"通过；现在改成带预发布规则的比较器集合判断，`>=0.1.6-0 <0.2.0` 对 `0.1.7-alpha.2` 会**失败**。

### 谁受影响

- 在 DSH `0.1.7-alpha.2` 上安装或升级本插件的人：现在能正常装入并显示。
- 从 `0.1.2` 升级的人：**标记数据不受影响**，`session-colors.json` 无需迁移；刷新页面即可拿到新客户端，宿主半边改动需要重启 `dsh web`。

### 兼容性与升级

```sh
dsh plugin --profile web add @idoall/dsh-session-colors@0.1.3
```

然后在 profile 的 `cordis.patch.yml` 里给一个数据目录，再**重启 `dsh web`**：

```yaml
- id: dsh-session-colors
  config:
    dataDir: /absolute/path/to/profiles/web/data/dsh-session-colors
```

不配 `dataDir` 也能用，但标记只活在宿主进程的生命周期里。宿主半边只在 DSH 启动时加载；客户端半边刷新页面即生效。

### 限制

- **色块依赖 DSH 的行 DOM**：靠 ARIA role 找行、靠行自身的 `data-row-key` 取会话 id（回退到 React fiber）。DSH 大改侧栏结构后色块可能不再显示；但**不会影响点击**，因为浮层从不接收指针事件。
- **标记属于单个 DSH 实例**：两个独立的 DSH 服务之间不共享。
- **没有权限模型**：能访问该 profile 已鉴权路由的人都能读写标记。
- **只有颜色**：没有文字标签、图标或 emoji。

### Why an adaptation was required

DSH `0.1.7-alpha.2` changed three things this plugin depends on. The first made
the old build fail to load at all (after a `link:` install the Host half could not
import); the second is a declaration error (the range does not cover the running
version under node-semver's default rules, so pnpm reports an unmet peer); the
third is a visible behaviour regression (a collapse, expand or reorder left the
chips at the position the glide started from). All three were checked against the
running instance's own source and manifests, not inferred:

1. **Linked-plugin dependency resolution changed.** From 0.1.7, only a linked
   plugin's **peer** dependencies resolve from the running installation; a plain
   `dependency` is looked up under the plugin's own `node_modules`, which a
   `link:` install does not populate. `@deepseek-ai/schemastery` was a plain
   dependency and this repository ships no `node_modules`, so after a `link:`
   install the Host half failed to import and **the plugin never loaded**.
2. **The peer range did not cover the release.** It read `>=0.1.6-0 <0.2.0`.
   Under node-semver's default rule a version that carries a prerelease is
   admitted only when some comparator names the same `major.minor.patch`, so
   `0.1.7-alpha.2` does **not** satisfy that range and pnpm reports it as an
   unmet peer. (The plugin market's discovery passes `includePrerelease`, so it
   showed "unknown" rather than "incompatible" — the declaration was still
   wrong.)
3. **The sidebar rows became animated.** 0.1.7 adds
   `data-row-key="session:<id>"` to every Session row and glides rows with the
   Web Animations API (`element.animate`), which fires neither `transitionrun`
   nor `transitionend` and mutates no DOM. The layer only opened its bounded
   follow window on a transition event, so a collapse, expand or reorder left
   the chips at the position the glide started from.

### What changed

- **The Host dependency is now a peer.** `@deepseek-ai/schemastery` moved from
  `dependencies` to `peerDependencies` (kept in `devDependencies` for this
  repository's own tests). DSH 0.1.7 then resolves it to the running
  installation's `3.18.4`, so a `link:` install no longer needs a local
  `pnpm install`.
- **The declared ranges match the release.** `dsh-client-ui-layout` /
  `dsh-client-ui-conversation` now declare `>=0.1.7-alpha.2 <0.2.0`, a
  `dsh.engines.dsh` requirement was added, and
  `dsh.compatibility.dshReleases` records `0.1.7-alpha.2`.
- **The Session id comes from the row itself.** `sessionIdOf()` reads
  `data-row-key` (the `session:` prefix) first and falls back to the React fiber
  — older builds and search-result rows still take the fallback, and both walks
  stay bounded and guarded.
- **Chips follow the animated rows.** Row add/remove, the `body` class, and
  `aria-expanded`/`hidden` mutations plus window resize all go through `kick()`:
  re-measure once, then enter the same 40-frame bounded follow window a CSS
  transition uses. The Web Animations glide is followed frame by frame; a body
  mutation unrelated to the row list re-measures once without opening a window,
  so a streaming transcript cannot keep a measuring loop alive.
- **Build marker** is now `host-routes+animated-rows`, so a DOM dump can tell a
  cached client apart.
- **The docs-consistency test was strengthened.** It used to check
  `range.includes('0.1.7')`, which is exactly how a range that excludes the
  running version passed; it now evaluates the comparator set with the
  prerelease rule, and `>=0.1.6-0 <0.2.0` **fails** for `0.1.7-alpha.2`.

### Who is affected

- Anyone installing or upgrading this plugin on DSH `0.1.7-alpha.2`: it now
  installs and shows.
- Upgrading from `0.1.2`: **marks are untouched** and `session-colors.json`
  needs no migration. Refresh the page for the new client; the Host half needs a
  `dsh web` restart.

### Compatibility and upgrade

```sh
dsh plugin --profile web add @idoall/dsh-session-colors@0.1.3
```

Then give it a data directory in the profile's `cordis.patch.yml` and **restart
`dsh web`**:

```yaml
- id: dsh-session-colors
  config:
    dataDir: /absolute/path/to/profiles/web/data/dsh-session-colors
```

It works without `dataDir`, but then marks live only for the life of the Host
process. The Host half loads only at DSH boot; the browser half reloads on a page
refresh.

### Limitations

- **Chips depend on DSH's row DOM**: rows are found by ARIA role and the Session
  id comes from the row's `data-row-key` (falling back to React internals). A
  large change to the sidebar structure can stop chips from appearing; it
  **cannot break clicking**, because the layer never accepts pointer events.
- **Marks are per DSH instance**: two independent DSH servers do not share them.
- **No permission model**: anyone who can reach the Host's authenticated routes
  for this profile can read and write marks.
- **Colour only**: no labels, icons, or emoji.
