| `0.1.4` | `0.1.7-rc.1`、`0.1.7-alpha.2` | 已发布 |

### 为什么发这个版本

官方发布了 `0.1.7-rc.2`，这是 `0.1.7` 系列的第二个候选版本。本版的作用是**确认并声明对新 RC 的支持**：`rc.1 → rc.2` 之间，本插件依赖的契约全部没有变化，所以这次同样没有新的适配工作，只有兼容性确认与声明更新。三条结论都来自运行实例与官方产物本身，不是推测：

1. **在运行中的 `0.1.7-rc.2` 实例上实测通过，用的是已发布的 `0.1.4`（其源码与本版逐字节相同）。** 控制台与浮层都报告 `build=host-routes+animated-rows`，`status=ready`、`marks=3`、`writable=true`；3 个真实标记的色块与各自的行**精确对齐**（`left=14`＝行 `left=12`+2，`top`＝行顶+8，偏差 0）；触发一次真实的 `AnimatedRows` WAAPI 滑动（折叠工作区，被标记行从 `top=700` 滑到 `632`，24 个不同位置）时色块逐帧跟随，瞬时偏差最大 5px、随后归零；选择器正常打开（`role=dialog`、`aria-label=选择会话颜色`、7 个主题色、5 个输入框、面板 `right=2048 ≤ 2056` 留在屏内）并按 Esc 关闭。验证过程未写入任何标记，宿主文件仍只有原来那 3 条。
2. **逐包核对了 rc.2 的实际产物。** `dsh-client-modules`（客户端加载器）与 `dsh-client-ui-slots`（slot 注册 API）的 `client.js` 与 rc.1 **逐字节相同**；`ui-workspace` 的会话行仍带 `data-row-key="session:<id>"`、`role="treeitem"`、`aria-selected`，行与色块相关的几何（`padding-inline-start: calc(8px + var(--dsh-workspace-indent))`、`height:32px`、16×20 的前置格、标题外边距）**没有变化**，只多了一个 `border-radius` 令牌；`ui-layout` 的 `shell.overlay` 与 `.overlayLayer`（`z-index:20`、`pointer-events:none`、子元素 `auto`）不变；`ui-conversation` 的 `conversation.session.header.utilities` 仍是 session 作用域的 list 座位；`ui-sidebar` 的 `--dsh-sidebar-inline-padding:12px` 与区域几何不变；`locale` 的 `register`/`bind` 不变。`app-boot` 的兼容性预检 `evaluatePluginCompatibility` 也**逐字节相同**——它这一版的改动只是把"跳过的 bundle"从 stderr 改为记入 `skippedBundles` 并新增一次性上报。
3. **预检对我们的声明判定为通过。** 预检用 `semver.satisfies(runtime, range, { includePrerelease: true })` 判定 `@deepseek-ai/dsh*` 的 peer；我们的 `>=0.1.7-alpha.2 <0.2.0` 对 `0.1.7-rc.2` 实测为 `true`。**范围不满足时 DSH 会直接禁用该插件行**，所以范围写对是"能不能加载"的问题，不是"声明好不好看"的问题。

### 改了什么

- **声明记录新 RC。** `dsh.compatibility.dshReleases` 现同时记录 `0.1.7-rc.2`、`0.1.7-rc.1` 与 `0.1.7-alpha.2`。
- **peer 与 `dsh.engines.dsh` 范围刻意保持不变。** 仍是 `>=0.1.7-alpha.2 <0.2.0`：按 node-semver 的预发布规则，只要范围里有比较符写了同一个 `major.minor.patch`，该版本的预发布就会被接纳，所以这个范围**同时覆盖**三个已声明版本。无需为第二个 RC 放宽范围，也就不会顺带接纳未经测试的版本。
- **代码零改动。** 两个半边与 `0.1.4` 完全一致；本版只改声明与文档。
- **文档。** 中英文 README 的顶部提示、安装要求与兼容性表格均更新到 `0.1.7-rc.2` / 插件 `0.1.5`；英文 README 里重复了一遍的 `@deepseek-ai/schemastery` peer 条目已删除（中文版本来就只有一条）。
- **设计记录。** 补记本次逐包核对结论、实测数据，以及下面这条产品选择。

### 一个已记录、但本次不实施的选择

`rc.2` 新增了真正的会话行座位 `sidebar.session.row.leading`（以及悬停卡片里的 `sidebar.session.row.hover`）。按 DSH 自己的说明，`leading` 座位落在**状态点那一格**，并且**只在行的主状态为空闲时才挂载**——运行中、等待审批、有新消息或已归档的行都不渲染占位（已归档行的该格留空）。本插件的产品不变量是"色块在任何状态下都可见，且永不盖住状态点"，所以把色块搬进该座位会在最需要它的时候让它消失。**本版保持浮层实现不变**，把这条选择记在设计记录里；是否将来改用该座位（或两者混用）留待明确决策，不在此次小版本中擅自改动。

### 谁受影响

- **正在使用 `0.1.7-rc.2` 的人**：直接升级即可，本版就是为这个版本发布的。
- **从 `0.1.4` 升级的人**：**标记数据无需迁移、配置无需改动**——代码与 `0.1.4` 相同，`session-colors.json` 照旧读取。
- **仍在更旧 DSH（含 `0.1.6-alpha.2`）的人：请继续用插件 `0.1.2`。** `0.1.5` 声明的宿主要求是 `>=0.1.7-alpha.2 <0.2.0`，低于它的版本未经本轮验证。

### 兼容性与升级

```sh
dsh plugin --profile web add @idoall/dsh-session-colors@0.1.5
```

然后在 profile 的 `cordis.patch.yml` 里给一个数据目录（若尚未配置），再**重启 `dsh web`**：

```yaml
- id: dsh-session-colors
  config:
    dataDir: /absolute/path/to/profiles/web/data/dsh-session-colors
```

宿主半边只在 DSH 启动时加载，所以升级后需要重启 `dsh web`；客户端半边刷新页面即生效。不配 `dataDir` 也能用，但标记只活在宿主进程的生命周期里。

从 `0.1.4` 升级不需要任何数据操作。

### 限制

- **色块依赖 DSH 的行 DOM**：靠 ARIA role 找行、靠行自身的 `data-row-key` 取会话 id（回退到 React fiber）。DSH 大改侧栏结构后色块可能不再显示；但**不会影响点击**，因为浮层从不接收指针事件。
- **色块不是行内占位元素**：它留在自己的点击穿透浮层上，而不是 `sidebar.session.row.leading` 座位里（原因见上）。
- **标记属于单个 DSH 实例**：两个独立的 DSH 服务之间不共享。
- **没有权限模型**：能访问该 profile 已鉴权路由的人都能读写标记。
- **只有颜色**：没有文字标签、图标或 emoji。

### Why this release exists

The harness published `0.1.7-rc.2`, the second release candidate on the `0.1.7`
line. This release **confirms and declares support for that RC**: every contract
this plugin depends on is unchanged between `rc.1` and `rc.2`, so there is again
no new adaptation work here, only a compatibility confirmation and a declaration
update. All three findings come from the running instance and the shipped
artifacts, not from inference:

1. **Verified on a running `0.1.7-rc.2` instance, using the published `0.1.4`
   (whose source is byte-identical to this release).** The console and the layer
   both report `build=host-routes+animated-rows`, with `status=ready`, `marks=3`
   and `writable=true`; the three real marks' chips align **exactly** with their
   rows (`left=14` = row `left=12` + 2, `top` = row top + 8, zero deviation);
   a real `AnimatedRows` WAAPI glide (collapsing a workspace, the marked row
   travelling from `top=700` to `632` across 24 distinct positions) is followed
   frame by frame with at most 5px of transient lag that then settles to 0; the
   picker opens normally (`role=dialog`, `aria-label=选择会话颜色`, seven theme
   swatches, five fields, panel `right=2048 ≤ 2056` inside the viewport) and
   closes on Esc. Nothing was written: the Host file still holds exactly the same
   three marks.
2. **Checked against the shipped rc.2 artifacts, package by package.**
   `dsh-client-modules` (the client loader) and `dsh-client-ui-slots` (the slot
   registration API) are **byte-identical** to rc.1; a `ui-workspace` Session row
   still carries `data-row-key="session:<id>"`, `role="treeitem"` and
   `aria-selected`, and every geometry the chip depends on
   (`padding-inline-start: calc(8px + var(--dsh-workspace-indent))`,
   `height:32px`, the 16×20 leading cell, the title margins) is **unchanged** —
   only a `border-radius` token was added; `ui-layout`'s `shell.overlay` and
   `.overlayLayer` (`z-index:20`, `pointer-events:none`, children `auto`) are
   unchanged; `ui-conversation`'s `conversation.session.header.utilities` is still
   the same session-scoped list seat; `ui-sidebar`'s
   `--dsh-sidebar-inline-padding:12px` and region geometry are unchanged; and
   `locale`'s `register`/`bind` are unchanged. `app-boot`'s compatibility
   preflight `evaluatePluginCompatibility` is **byte-identical** too — its rc.2
   change only moves skipped bundles from stderr into `skippedBundles` plus a
   one-off report.
3. **The preflight accepts our declaration.** It calls
   `semver.satisfies(runtime, range, { includePrerelease: true })` over the
   `@deepseek-ai/dsh*` peers; our `>=0.1.7-alpha.2 <0.2.0` measures `true` for
   `0.1.7-rc.2`. **When the range is not satisfied, DSH disables the plugin row
   outright**, so a correct range is about loading, not about appearances.

### What changed

- **The declaration records the new RC.** `dsh.compatibility.dshReleases` now
  records `0.1.7-rc.2` alongside `0.1.7-rc.1` and `0.1.7-alpha.2`.
- **The peer and `dsh.engines.dsh` ranges deliberately stay unchanged.** They are
  still `>=0.1.7-alpha.2 <0.2.0`: under node-semver's prerelease rule a version's
  prerelease is admitted when some comparator names the same `major.minor.patch`,
  so that one range covers **all three** declared releases. There is no need to
  widen it for the second RC, and widening would admit versions nobody tested.
- **Zero code change.** Both halves are identical to `0.1.4`; this release
  changes declarations and documentation only.
- **Documentation.** Both READMEs' top banner, install requirements and
  compatibility tables now state `0.1.7-rc.2` / plugin `0.1.5`; the English README
  had its duplicated `@deepseek-ai/schemastery` peer bullet removed (the Chinese
  README already carried it once).
- **Design record.** It now notes this package-by-package check, the measurements
  above, and the product choice below.

### A recorded choice, not implemented in this release

`rc.2` adds a real Session-row seat, `sidebar.session.row.leading` (plus
`sidebar.session.row.hover` for the hover card). By DSH's own documentation the
`leading` seat sits in **the status dot's own cell** and is mounted **only while
the row's primary state is idle** — a running, waiting, newly-messaged or archived
row renders no occupant there (an archived row leaves the cell blank). This
plugin's invariants are that a chip is visible in every state and never covers the
status dot, so moving the chip into that seat would make it vanish exactly when it
is most useful. **This release keeps the overlay implementation unchanged** and
records the choice in the design record; adopting the seat (or a hybrid) is left
to an explicit decision rather than smuggled into a small release.

### Who is affected

- **Anyone on `0.1.7-rc.2`**: upgrade directly — this release exists for that
  version.
- **Upgrading from `0.1.4`**: **marks need no migration and config no change** —
  the code is identical to `0.1.4`, and `session-colors.json` is read as before.
- **Anyone still on an older DSH, including `0.1.6-alpha.2`: stay on plugin
  `0.1.2`.** `0.1.5` declares its Host requirement as
  `>=0.1.7-alpha.2 <0.2.0` and is not verified below it.

### Compatibility and upgrade

```sh
dsh plugin --profile web add @idoall/dsh-session-colors@0.1.5
```

Then give it a data directory in the profile's `cordis.patch.yml` (if it does not
have one yet) and **restart `dsh web`**:

```yaml
- id: dsh-session-colors
  config:
    dataDir: /absolute/path/to/profiles/web/data/dsh-session-colors
```

The Host half loads only at DSH boot, so an upgrade needs a `dsh web` restart; the
browser half reloads on a page refresh. It works without `dataDir`, but then marks
live only for the life of the Host process.

Upgrading from `0.1.4` needs no data operation.

### Limitations

- **Chips depend on DSH's row DOM**: rows are found by ARIA role and the Session
  id comes from the row's `data-row-key` (falling back to React internals). A
  large change to the sidebar structure can stop chips from appearing; it
  **cannot break clicking**, because the layer never accepts pointer events.
- **The chip is not a row occupant**: it stays on its own click-through layer
  rather than in the `sidebar.session.row.leading` seat (see above).
- **Marks are per DSH instance**: two independent DSH servers do not share them.
- **No permission model**: anyone who can reach the Host's authenticated routes
  for this profile can read and write marks.
- **Colour only**: no labels, icons, or emoji.
